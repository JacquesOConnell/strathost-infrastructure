# Terraform state bootstrap

This implements the state-storage design in section 5 of the [technical plan](../TERRAFORM-IMPLEMENTATION-PLAN.md). It defines state storage before workload modules can use a remote backend. **Schema validation and three mocked test runs pass with AWS provider 6.73.0. No infrastructure has been deployed.**

The bootstrap starts with Terraform's local backend. After an explicitly approved deployment, copy `backend.tf.example` to the ignored `backend.tf`, fill an ignored `backend.hcl` from the example, and migrate with `terraform init -migrate-state -backend-config=backend.hcl`. Confirm the bucket, key, encryption key and AWS account before migration. Preserve a controlled recovery copy. Do not add the remote backend before its bucket exists.

## What is used and why

| Selection | Reason |
|---|---|
| Terraform 1.17.2 and AWS provider 6.73.0 | Exact research baseline from the plan; reproducible schema and CLI behaviour |
| Separate bootstrap root | Avoids depending on a state bucket that does not exist yet |
| Dedicated S3 bucket | Separates infrastructure state from application backups and logs |
| Versioning and 365-day noncurrent retention | Preserves state history while bounding old-version retention; current state is not expired |
| Customer-managed KMS key with rotation | Separate administrative and cryptographic access; encrypted state and bucket keys |
| Thirty-day key deletion window and prevent_destroy | Adds protection against accidental loss of the state bucket and its encryption key |
| BucketOwnerEnforced and all four public access blocks | Disables ACL ownership ambiguity and public access paths |
| TLS and encryption policy denies | Rejects insecure transport, explicit wrong algorithms or key headers, and SSE-C; absent encryption headers can use bucket defaults |
| S3 native lock files | Coordinates state writes without a DynamoDB lock table |
| Exact state-key permissions | Allows state reads/writes and lock creation/removal; grants DeleteObject only on lock objects |
| Required account and existing role inputs | Prevents accidentally selecting the unrelated Checkmk development account or inventing account identities |
| Unattached backend policies | Leaves existing identity ownership with its administering stack; review the output role-policy mapping before attachment |
| Shared bootstrap tagging | The bucket serves several explicit environment state paths; workload resources will retain environment-specific tags |

The key's account-root statement enables controlled IAM delegation and recovery. Explicit administrator roles manage the key; backend cryptography is restricted to regional S3 and the bucket encryption context. Bucket Keys use the bucket ARN as that context. These policies must still be tested against real backend operations before deployment acceptance. Other existing IAM policies, SCPs and permissions boundaries can affect effective access.

Credentials are resolved externally through an approved AWS profile or role session. No credentials are stored in these examples. The account and ARNs in examples are fictitious. Backend credentials and provider credentials are resolved independently. Runtime EC2 roles must never receive these backend policies.

## Current boundary

Networking, security, encryption and storage have been added separately; environment composition and remaining workload modules are still pending. Backend permissions, state migration, lock contention, history recovery and KMS usage have not been live-tested. The generated bootstrap lockfile includes provider package checksums for Windows AMD64 and Linux AMD64; execution checks so far ran on Windows only. No `apply` is authorised by the implementation request alone; the master plan requires explicit account, scope and cost approval for deployment.

The mock tests cover state storage controls, required tags, native-lock configuration and rejection of wildcard keys and cross-account roles. Their policy-document data is mocked: these tests do not validate the rendered IAM JSON or effective permissions. Before acceptance, inspect the real provider-rendered documents and test authorised and denied state/lock operations in the approved account.

```powershell
terraform -chdir=bootstrap init -backend=false
terraform -chdir=bootstrap validate
terraform -chdir=bootstrap test
terraform -chdir=bootstrap providers lock -platform=windows_amd64 -platform=linux_amd64
```

Retain the generated lockfile in source control when this work is committed. The provider was downloaded from HashiCorp and its Windows/Linux package signatures were verified by Terraform's provider installer; the lockfile was generated by Terraform, not written manually.
